# AI usage log

**Tools.** Claude (Anthropic) as a coding agent, with a shell, Docker and web search, used for research, code, tests and drafting docs. Configured model id `claude-opus-5-5`. A later pass in Cursor ran the suite on my own machine; that pass is entry #10.

**Working rule for this repo.** The AI wrote most of the code. No safety claim counts until a test shows it, and no test counts until breaking the protection turns it red (mutation testing). Most of the corrections below came out of that rule.

| # | What I asked AI to do | What it produced | What I did with it |
|---|---|---|---|
| 1 | Research the architecture before writing any code | A recommendation: Temporal workflows instead of pod-per-agent, gVisor, a tool gateway plus an egress proxy, and the Agent Sandbox CRDs. It cited Temporal's hard limit (51,200 events / 50 MB) and GKE's warm-pool numbers. | **Accepted. The arithmetic holds:** a 100k-token context is about 400 KB per activity input, so inline payloads hit 50 MB in about 100 turns. That made claim-check mandatory rather than optional, which became a design constraint (§2). See #8 for where it was clearly better than me. |
| 2 | Write a test that the sandbox can't reach the Docker host | A probe of the subnet's `.1` address (the usual bridge gateway), expecting "not refused" | **Overrode.** When I removed the `inhibit_ipv4` fix the probe went red, as it should. But after I restored the fix *it stayed red*. With no gateway, the proxy takes `.1`, so the probe was hitting the proxy, and it would have passed or failed for the wrong reason. I replaced it with a sweep of the whole /28, excluding the sandbox and the proxy, and confirmed it is green on the fix and red on the mutant. Lesson: a security test that was never seen failing is unverified. |
| 3 | Write a test that a leaked proxy session credential can't be used from another sandbox | The test took sandbox B's whole `HTTPS_PROXY` URL and used it from sandbox A | **Overrode.** It failed with "connection refused", because B's proxy address is on B's network and unroutable from A. That is a real property, but not the one being claimed (that sessions are bound to a source IP). I rewrote it to put B's credential on A's own proxy address and expect a 407, kept the unroutable check as a separate assertion, and mutation-checked it: removing the IP check makes it fail. |
| 4 | Make the network guard refuse names that resolve to the metadata address | The guard worked, but the proxy reported the block as `502 egress_failed` (an upstream error) | **Changed to `403 egress_denied` with a `deny` audit record.** A model treats a 502 as flaky and retries, and an auditor would read it as an outage. A policy block has to look like a policy block to both of them. |
| 5 | Make the sandbox network isolated | The first plan used a Docker `internal: true` network per session | **Verified before trusting it, and it was wrong.** A probe from inside got HTTP 200 from a service on the host through the bridge gateway. `internal` only removes the route out; it doesn't remove the host. Fixed with `inhibit_ipv4`, now tested (#2). This also became a design note: check that NetworkPolicy blocks node IPs, which depends on the CNI. |
| 6 | Write the services Dockerfile | A `chown` in the builder stage, followed by `COPY` into `scratch` | **Fixed.** `COPY` resets ownership to root, so the non-root mocks couldn't write their CA files and the stack didn't start. Writable directories are now created with `COPY --chown`. Small, but it's the kind of thing that breaks "runs with one command" on the reviewer's machine. |
| 7 | Demo expectations for denied requests | A check of curl's exit code | **Fixed.** `curl -sS` exits 0 when the proxy returns a 4xx/5xx body. The expectations now check what the model would actually see (the denial reason, no credential material), not the process exit status. |
| 8 | Talk to the Docker Engine API with the standard library only (no SDK) | A hijacked `POST /exec/{id}/start` with stdin half-close and demultiplexing of Docker's 8-byte stream frames, with per-stream output caps that keep draining | **AI was clearly better than I would have been alone.** I would have pulled in the Docker SDK or spent an evening in the API docs. It was right first time, and the e2e suite exercises it hundreds of times. A dependency-free proxy and executor is also less to audit. |
| 9 | Measure cold start | A bench that only reported concurrent cold start (4.3 s p50) | **Extended.** That number alone suggests "sandboxes are slow". I added a one-at-a-time baseline (420 ms) and a per-phase breakdown. Under contention the cost is mostly network setup, which is a Docker artefact. That changed what the design says: warm pools are required for the burst, but per-sandbox start is not the problem. |

I then installed `runsc` release-20260928.0. `make demo` passed. Eight safety tests passed. `TestSandboxConfinement` did not (`WaitPID ... EOF`, sandbox gone), which is why that test stays a runc result in the README. |
